## Post-1.0 — work that appeared after the release

**Why this section exists.** Phases 0–3 were a build plan, and the build finished on 2026-09-07.
Everything found since falls outside all four phases, and outside the `phase-N` issue labels — so
until 2026-09-08 the two newest defects in the project were invisible to every tracking mechanism it
had. Numbering here is deliberately not `4.x`: this is not a fifth phase, it is what is open now.

- [x] **P1 Make the cost-brake checker vendor-aware.** ([#106](https://github.com/mathew-builds/Handoff/issues/106)) `scripts/check-workflow-caps.py` treated a step as running the agent only if its action came from `anthropics/`, so a second agent's workflow contained no agent step and its turn cap went unchecked. Reproduced 2026-09-07: an uncapped `templates/codex.yml` using another vendor's action passed at **exit 0**. Subtler than the bug in the checker's own header — that one *asserted* a brake it had not checked; this one stayed silent and passed. *Accept:* the same uncapped input **fails**, demonstrated in both directions, and the case joins the mutation suite. **Done 2026-09-08.**
    - **The fix is an inversion, not a longer list.** Brake 3 is now found by looking for the *brake* (`CAP_FLAGS`) rather than for a *vendor*, and any workflow not explicitly declared turn-free in `NO_AGENT` must show one. "We don't recognise this workflow" used to mean *skip*; it now means *fail*. A vendor allowlist would have needed extending for every new agent, and forgetting would have failed silently — which is the defect, not the fix.
    - **Proven in both directions, in that order.** The test was written first and watched fail (`exit 0, wanted 1`) against the unfixed script; then the fix; then the same byte-identical input at **exit 1**. A check that has never failed has not been tested.
    - **Two cases, not one.** A control was added — a second-vendor workflow that *is* capped, which must still pass. Without it the suite would be satisfied by a checker that failed every unrecognised workflow unconditionally, which would look correct and would make a capped second agent unshippable.
    - **Not covered:** no second agent exists, so this is proven against a synthetic workflow rather than a real one. `AGENT_PREFIX` is still `anthropics/` and still vendor-specific, deliberately — it is what catches `claude.yml` having its action swapped for a wrapper, which is a different guard from brake 3.
- [x] **P2 The pull-request report-back only ever says `tests pending`.** ([#108](https://github.com/mathew-builds/Handoff/issues/108)) *Accept:* a passing pull request produces green and a failing one produces red, both observed with run IDs in `07-evidence.md`. **Done 2026-09-08.** Trial PR 16 (passing) → `**Checks green** — 1 of 1 passed.`; PR 17 (deliberately failing) → `**Checks red** — 1 of 1 failed.` Runs `34156121781`, `34156121772`, `34156104908`. Both branches had never run anywhere before.
    - **Fixed with a new optional workflow, not by changing the routine.** `templates/pr-checks-report.yml` posts a second comment once the checks settle. `gh` and shell, **no model turns**, and it assumes nothing about any chat vendor's connector — which sidesteps the unverified question of whether one can trigger on check completion at all.
    - **The first design was wrong and the way it failed is the finding.** It triggered on `check_suite: completed` — no configuration needed — and produced **zero runs** while CI went green on one pull request and red on another. GitHub documents the reason: that event does not trigger workflows when the check suite was created by GitHub Actions, to prevent recursion. So it can never report on CI that runs in Actions, which is every consumer. `workflow_run` is the documented alternative and needs the upstream workflow named by its `name:` field.
    - **Not covered:** one CI check on a small repository. The aggregate across several suites, fork pull requests, and `neutral`/`skipped` conclusions are coded for and unobserved. Naming the upstream workflow wrongly makes this fail silently — the same failure mode it exists to fix — so it is flagged in the template header, not buried.
